# 写测试

为一项代码改动写测试，按「红 → 绿 → 补」三明治推进：**先写失败用例，再实现让它通过，最后补齐边界**。测试是行为的可执行文档，写出来的测试要能回答「这个函数保证什么」。

## 流程

1. **先读实现与调用方，确定行为契约。** read 目标文件与调用方，找出：正常输入应返回什么、边界输入（空、超长、越界、非法格式）应如何处理、异常应怎么报。契约写清楚了，测试才有断言依据。
2. **写失败用例（红）。** 按契约先写核心正常路径的测试——不改实现直接跑，测试应失败（证明测试真的在测，不是摆设）。同一契约下每条断言独立成例，能单独指出哪条行为坏了。
3. **实现让测试通过（绿）。** 实现改动，跑测试直到全绿。测试失败时按「错误即数据」看失败信息定位，不要盲改。
4. **补齐边界与异常（补）。** 空输入 / 边界值 / 异常路径 / 并发与顺序依赖，逐条补用例；每条边界用例都要能说明「为什么这条行为值得被钉死」。
5. **跑全量验证。** 用项目既有命令跑相关测试与类型检查（bun test / bun run typecheck 等），确认改动不破坏既有行为，并把结果如实报告。

## 原则

- **测试与被测行为一一对应**：一条断言对应一个行为，失败时一眼看出哪个保证被破坏。
- **覆盖边界不等于凑行数**：优先异常路径与边界值，不是每个分支都要一行行铺。
- **不要为测试而测试**：测不出问题的测试（永远通过的断言、没断言的用例）不如不写。
- 遵循项目既有的测试框架与命名约定（先 glob 现有 `*.test.ts` 看风格）。
