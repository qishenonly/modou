# 写 commit message

把一组工作区改动整理成一条清晰、可追溯的 commit message。commit message 是给「半年后的自己」和协作者看的：主题说明改了什么，正文说明为什么。

## 流程

1. **先看清改动是什么。** 用 bash 拿改动清单与 diff（`git status` / `git diff --stat` / `git diff` 或 `git diff --cached`），确认本次提交实际包含哪些文件、哪些行为变化。改动没看清就写 message，主题必然失真。
2. **看仓库既有约定。** 读 README / AGENTS.md / 历史提交（`git log --oneline -20`），确认仓库用的是 Conventional Commits（`feat:` / `fix:` / `refactor:`…）、还是其他风格。类型与格式跟着仓库走，不发明自己的风格。
3. **写主题（第一行）。** `<type>(<scope>): <一句话>`
   - type 取既有约定；拿不准用 `chore`。
   - scope 是受影响模块（可省）。
   - 主题一句话讲清「改了什么行为」，用祈使句、控制在 50 字符内；不要只写「修复 bug」这种无信息量的话。
4. **需要时写正文。** 改动跨多文件、行为有取舍、或修复了非显而易见的坑时，正文补充：
   - **为什么**（动机、取舍、修了什么坑）——这是正文最重要的部分；
   - 关联的上下文（issue / 设计文档编号）。
   - 正文格式：空一行接在主题后，每条一短段。
5. **对照校验。** 主题 + 正文应能回答「改了哪、为什么」；与 diff 里实际改动逐条核对，不要写 diff 里没有的承诺。

## 原则

- 一条提交只讲一件事；改动本身跨多个主题时，拆成多条提交而非写成长篇。
- 正文解释「为什么」不解释「怎么改」——怎么改 diff 里看得见。
- 诚实：不夸大影响面（别把「改了个函数」写成「重构整个模块」）。
