# 代码审查

审查一份代码改动（提交、PR、或工作区 diff），目标是找出**会导致线上事故、行为偏差、或后续维护负担**的问题，而不是逐行挑风格。

## 流程

1. **先看 diff 全貌，再读代码。** 用 bash 拿改动清单（`git diff --stat` / `git log -p` 等），先建立「改了哪些文件、各改了多少」的整体图景，不要一头扎进某个文件。diff 看不清的（重命名、跨文件改动）再回源文件核对。
2. **逐文件审查，按文件分组输出。** 每个文件独立给出意见；同文件内多条意见按严重度排序。先通读该文件改动，再读被改函数/模块的既有上下文（read 目标函数前后、grep 调用方），判断改动是否与既有设计一致。
3. **按严重度分级，只有三类：**
   - **阻断（blocking）**：会导致错误行为 / 崩溃 / 数据丢失 / 安全漏洞，必须修。给出具体场景（哪条路径、什么输入会触发）。
   - **建议（suggestion）**：边界没覆盖、错误处理缺失、与既有约定不一致，值得改。说明理由，不强制。
   - **风格（nit）**：可改可不改，一条带过，不展开。
4. **验证判断，不猜。** 说「这段逻辑有 bug」必须能指出具体输入走到哪一行出错；拿不准就 read/grep 确认后再下结论。不要基于残缺信息断言。
5. **给出结论。** 每条意见格式：`[严重度] 文件:行号 — 问题 — 建议改法`。结尾总结：是否可合并/合并前必改项。

## 原则

- 改动引入的**新问题**优先于既有代码的老问题；老问题只在被改动行附近顺带提一句。
- 安全相关（注入、越权、敏感信息）一律阻断级。
- 只审查改动本身，不借机重构未改动的代码。
