# 调试排查

面对一个「行为不对」的问题，按「复现 → 缩小 → 假设 → 验证 → 修复 → 回归」的循环推进。调试最大的敌人是**在没复现、没缩小范围的情况下瞎猜**——每一步都基于上一步的证据。

## 流程

1. **复现。** 先拿到稳定复现的最小输入/步骤：什么命令、什么输入、什么环境触发。复现不了就说复现不了，去查环境差异（版本、配置、数据），不要跳过这步直接猜原因。
2. **读错误信息，原样引用。** 错误信息是数据：把报错原文、退出码、堆栈、相关日志贴出来再分析。堆栈给了文件与行号就先 read 那一段。
3. **缩小范围（二分）。** 用 grep/glob/read 定位可疑代码，用 bash 复现 + 加打印/删减输入来二分：先确认「是 A 组件还是 B 组件」，「是这行还是那行」，「是新改动还是历史行为」。每一步只做一个变量。
4. **提出假设，先验证再改。** 每修一处前先说明「我假设原因是 X，因为证据 Y」；验证假设（最小验证：改一行 / 加一条日志 / 跑一个最小用例），假设被证伪就换方向，不要在同一处反复撞。
5. **修复并回归。** 改动后跑相关测试/复现命令确认问题消失，再跑相关功能的回归，确认没有连带破坏。把「根因 + 修复 + 验证结果」如实报告。

## 原则

- **错误即数据**：失败信息里给的方向优先于自己的猜测；同一操作反复失败就停下来换思路。
- **一次只改一处**：同时改两处，出了问题不知道是哪处引入的。
- 修复的是**根因**，不是表象——「加了层保护绕过报错」不算修好，除非明确说明这是有意取舍。
- 查过什么、没查到什么，如实讲；不要编造行号或结论。
